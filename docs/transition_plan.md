> PROJECT_BRIEF 0장 4번 산출물 (원래 "FRQ 데이터 이전 계획"에서 변경) · 2026-10-01 초안 (승인 대기)

## 1. 목표와 원칙

| 원칙 | 내용 |
|---|---|
| 서비스 중단 없음 | 새 플랫폼이 열리기 전까지 기존 앱은 평소대로 운영한다. 전환일에도 학생이 FRQ를 못 보는 날이 없게 한다 |
| 데이터 손실 없음 | 전환 직전 기존 DB를 **완전 백업**(`pg_dump` + Storage, 암호화)한다. 기존 DB는 전환 뒤에도 일정 기간 그대로 보존한다 |
| 기존 DB는 읽기만 | 이전 스크립트는 기존 DB를 **읽기 전용**으로만 접근한다. 기존 앱 스키마는 끝까지 바꾸지 않는다 |
| 검증 후 반영 | 모든 이전은 **새 개발 DB → 검증 → 새 운영 DB** 순서로 한다. 스크립트는 여러 번 실행해도 결과가 같다 |
| 되돌릴 수 있음 | 출시 후 일정 기간은 기존 앱으로 되돌아갈 수 있게 둔다 (6장) |

## 2. 이전 대상

| 대상 | 처리 | 결정 상태 |
|---|---|---|
| FRQ 문항 (현재 13개, 전환 시점에 더 늘 수 있음) | `items` + `item_versions`. 복제로 생긴 중복은 내용 해시로 합침 | **이전 확정** |
| 루브릭 (`parsed_rubric`) | `frq_parts` / `frq_scoring_points` (계보 새로 부여). 원본 루브릭 텍스트·이미지는 `key/` 자산으로 | **이전 확정** |
| 문제·루브릭 이미지 | Storage 복사 (`stem/` / `key/` 분리) | **이전 확정** |
| AP Unit·topic | `item_courses`(AP Chem) + 단원 매핑. topic 자유 텍스트는 메모로 보존 (개념 태그는 E1에서 새로) | **이전 확정** |
| 시험지 구성 | (선택) `assessments` 초안으로 재현. 배정·응시 기간은 옮기지 않음 | 출시 직전 결정 |
| 학생 명단 | 이전하지 않는다. 엑셀 일괄 초대로 새 계정 생성 (이메일 동일) | 확정 |
| 반(클래스) 구성 | 이전하지 않는다. 새 플랫폼에서 반을 만들고, 엑셀로 반 배정 | 확정 |
| 교사·TA 계정 | 새로 초대 | 확정 |
| **과거 응시** (제출·답안·채점·검수) | 설계안 10.2 경로로 가져올 수 있음. 루브릭 버전이 같을 때만 포인트 단위 | **T-14일에 결정** |
| 비용 기록 | 이전하지 않는다. 기존 앱 대시보드를 CSV로 내보내 보관 | 확정 |
| 알림·공유 링크·세션 | 이전하지 않는다 | 확정 |

## 3. 일정 (T = 새 플랫폼 출시일)

> 전환일은 **응시 기간이 열려 있는 시험이 없는 주간**으로 잡는다. 예를 들어 학기 사이나 방학 시작 직후다.

| 시점 | 작업 | 담당 | 완료 기준 |
|---|---|---|---|
| **P3 진행 중** | `scripts/import-legacy-frq` 개발. 최신 **백업 파일**을 입력으로 새 **개발 DB**에 반복 실행 | Claude | 문항·파트·포인트·이미지 수 일치, 교사 화면에서 렌더링 확인 |
| | (과거 응시 경로를 쓸 경우) 같은 스크립트의 attempts 단계 개발·검증 | Claude | 표본 10건의 점수·포인트 결과가 기존 앱 화면과 일치 |
| **T-14일** | 결정 회의: ① 과거 응시 이전 여부 ② 시험지 구성 재현 여부 ③ 전환일 확정 ④ 학생·보호자 공지 문안 | 운영자 | 결정 기록 |
| **T-10일** | 학생·보호자 공지 (새 주소, 로그인 방식 변경, 화면 이탈 기록 안내, 동의서) | 운영자 | 공지 발송 |
| **T-7일** | 새 운영 DB에 반·명단 엑셀 등록 → **초대 메일 발송** (학생·TA). 보호자 동의 수집 시작 | 운영자 + Claude | 초대 수락률 확인 (목표: T-1일까지 100%) |
| **T-5일** | 기존 앱에서 진행 중인 시험이 모두 마감·채점됐는지 확인 (Batch 대기열 0건, 미검수 0건) | 운영자 | 대기열·미검수 0 |
| **T-3일** | **콘텐츠 동결:** 기존 앱에서 문항·루브릭 추가·수정 중단 | 운영자 | — |
| **T-2일** | **기존 DB 완전 백업** (`pg_dump` 역할·스키마·데이터 + Storage, 암호화). 보류 항목이 여기서 반드시 실행됨 | Claude (+운영자 DB 접속 정보) | 암호화 파일 생성, 복원 시험 1회 (빈 프로젝트) |
| **T-1일** | 새 **운영 DB**에 최종 이전 실행 → 자동 검증 → 교사 화면 표본 확인 | Claude + 운영자 | 4장 체크리스트 전부 통과 |
| **T (출시)** | 새 플랫폼 공개. 기존 앱을 **읽기 전용 모드**로 전환 (아래) | 운영자 + Claude | 학생 첫 로그인 성공 |
| **T ~ T+28일** | 기존 앱 읽기 전용 유지 (학생은 과거 결과 열람만). 새 플랫폼 안정화 | — | 6장 롤백 조건 미발생 |
| **T+28일** | 기존 앱 종료: 마지막 완전 백업(암호화) → Vercel 프로젝트 비활성 → 기존 도메인은 새 주소로 리디렉트 | 운영자 + Claude | 리디렉트 동작 |
| **T+90일** | 기존 Supabase 프로젝트 일시정지 → 백업 보존 기간 만료 시 삭제 | 운영자 | — |

**기존 앱 읽기 전용 모드:** 기존 앱의 새 응시와 시험 생성을 막는 **코드 변경**(환경변수 플래그 1개)이다. DB 스키마는 바꾸지 않는다. 플래그를 끄면 원래대로 돌아간다. 이 변경은 P3 중에 미리 만들어 둔다.

## 4. 이전 검증 체크리스트 (T-1일)

| # | 항목 | 방법 |
|---|---|---|
| 1 | 문항 수 | 기존 `questions`(중복 제거 후) = 새 `items`(source=legacy) |
| 2 | 파트·채점 포인트 수와 배점 합 | 문항별로 기존 `parsed_rubric` 합계 = 새 `frq_parts`/`frq_scoring_points` 합계 |
| 3 | 이미지 | 파일 수 + sha256 일치, 학생 화면 렌더링 표본 5문항 |
| 4 | 정답 정보 분리 | 학생 계정으로 content API 호출 시 루브릭·해설 필드 없음 (자동 테스트) |
| 5 | (과거 응시 시) 점수 | 응시별 총점이 기존 앱(검수 반영 점수)과 일치. 불일치 0건 |
| 6 | (과거 응시 시) 포인트 결과 | 루브릭 버전 일치 응시는 포인트 행 생성, 불일치는 원본 JSON만 (`legacy_rubric_mismatch`) — 건수 보고 |
| 7 | 학생 연결 | 과거 응시의 학생 이메일 → 새 profile 매칭률. 미매칭은 목록으로 보고 |
| 8 | AI 채점 동작 | 이전된 FRQ 1문항으로 새 플랫폼 채점 1회 실행 → 정상 |
| 9 | 백업 | T-2일 완전 백업 파일의 복원 시험 결과 |

## 5. 출시 직후 운영 (T ~ T+7일)

- 첫 시험은 **짧은 FRQ 퀴즈**로 시작한다. 모의고사는 둘째 주부터 진행한다.
- 매일 확인: 응답 유실 점검 스크립트, 검토 대기·자동 종료 건수, 채점 실패, 비용
- 학생 문의 창구: 로그인 문제와 초대 메일 재발송

## 6. 롤백 계획

| 조건 (T+28일 이내) | 조치 |
|---|---|
| 응답 유실, 채점 장애 등 **응시를 계속할 수 없는 문제**가 1일 안에 해결되지 않음 | 기존 앱의 읽기 전용 플래그를 끄고 FRQ 운영을 기존 앱으로 되돌린다. 새 플랫폼의 데이터는 그대로 보존하고, 문제를 고친 뒤 다시 전환한다 |
| 일부 기능 문제 (리포트, 화면 오류 등) | 롤백하지 않고 새 플랫폼에서 수정 |

- 되돌리는 기간에 기존 앱에서 생긴 응시는, 다시 전환할 때 "과거 응시" 경로로 가져올 수 있다.
- T+28일 이후에는 롤백하지 않는다. 기존 앱은 백업으로만 남는다.

## 7. 위험과 대응

| 위험 | 대응 |
|---|---|
| 초대 메일이 스팸함에 들어가거나 미수락 | 발송 도메인 인증(SPF/DKIM). T-7일 발송으로 여유 확보. 교사 화면에서 재발송 |
| 전환일에 진행 중인 시험 | 전환일을 응시 기간이 없는 주간으로 잡음. T-5일 확인 |
| 이전 후 루브릭 표시가 기존과 다름 | P3 중에 개발 DB에서 반복 검증하고, 교사가 표본 확인 |
| 기존 DB 접속 정보 노출 | 운영자가 `.env.local`에 직접 입력. 작업 후 DB 비밀번호 재설정 |
| 백업 평문 노출 | 설계안 7.1: 생성 즉시 암호화, 개인 PC에는 작업 중에만 |
