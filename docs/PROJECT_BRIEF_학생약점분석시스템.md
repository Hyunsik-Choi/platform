# 프로젝트 브리프: AP Chemistry 학생 약점 분석 시스템 (v3.1)

> **이 문서의 용도**
> 이 문서는 Claude Code가 개발 계획과 시스템 구조를 설계하기 위한 기준 문서다.
> 목적, 현재 상태, 설계 원칙, 데이터 구조, Error Taxonomy 기준, 기능 요구사항, 단계별 개발 계획을 담고 있다.
> 이 문서의 내용은 채팅에서 여러 차례 검토를 거쳐 확정한 것이며, "미결정 사항"으로 표시된 부분만 아직 열려 있다.
>
> **v3.1 변경 사항**
> - **C1·E 계열 오류도 유사 문제를 배정한다.** C1은 "교사 확인 필요" 표시를 병행한다. E 계열(FRQ)의 유사 문제는 FRQ 채점기가 연결되는 단계 4부터 제공한다.
> - **문항 출처는 선택 입력 필드로 변경**했다. 기본값은 "자체 제작"이다.
> - 1단계 평가에 C1·E 계열 재발률 비교를 추가했다.
> - "확인 문항"의 정의와 1단계에서의 대체 방식을 용어에 명시했다.
>
> **v3 변경 사항**
> - **구현 범위를 1단계로 축소:** 문제 태깅 → 에러 분석(단순 집계, 데이터 축적 목적) → 처방은 문항은행의 유사 문제 제공.
> - **"설계는 최종형, 구현은 최소형" 원칙 도입:** 데이터 구조는 최종 형태 기준으로 설계하고, 기능은 단계별로 필요한 만큼만 구현한다.
> - **1단계를 세분화:** ① 모의고사 2~3세트로 첫 출시 → ② 문항은행 전체 확장과 유사 문제·진단고사 → ③ 기존 FRQ 채점기 연결.
> - 약점 상태 4단계, 처방표, 확인 문항, 교사 개입 추천은 **1단계 평가 후 최종 형태에서 구현**한다.
>
> **v2 변경 사항 (유지)**
> - 종이 OMR 응시를 전면 제외. 모든 시험은 태블릿·PC로만 응시한다.
> - 학생 확신도 체크는 진단고사에서만 사용하며, 시험 세트별 설정으로 구현한다.
> - 모의고사의 불확실성 신호로 다시 보기 표시, 답 변경 이력, 소요 시간을 필수 수집한다.

## 0. Claude Code에게 요청하는 첫 번째 작업

**코드를 수정하기 전에** 다음 순서로 진행하고, 각 산출물을 보고한 뒤 승인을 받을 것. (9장 단계 0~1에 해당)

1. **현황 분석서:** 현재 운영 중인 FRQ 자동 채점 프로그램의 구조를 분석한다.
   - 사용 기술(언어, 프레임워크, 데이터베이스, 배포 방식)
   - 폴더 구조와 주요 파일의 역할
   - 데이터 구조: 문항, 루브릭, 학생, 답안, 채점 결과의 저장 형태
   - 학생 답안 원본(이미지·텍스트)의 보존 여부
   - FRQ 답안 입력 방식과 채점 흐름 (입력 → 채점 → 결과)
   - 로그인, 권한, 학생 계정·ID 관리 방식
2. **통합 설계안:** 이 문서의 **최종 형태 전체**(5장)를 기준으로 기존 FRQ 시스템과 통합하는 데이터 구조(엔티티 관계도 포함)와 모듈 구조를 제안한다. 각 테이블·모듈이 어느 개발 단계에서 실제로 구현되는지 함께 표시한다.
3. **학생 계정·ID 통합 방식:** 새 MCQ 기능이 처음부터 기존 FRQ 시스템과 같은 학생 ID 체계를 쓰도록 제안한다.
4. **FRQ 데이터 이전 계획:** 단계 4에서 실행할 이전 방법. 운영 서비스 중단과 데이터 손실이 없어야 한다.
5. **개발 계획:** 9장의 단계별 작업을 기준으로 세부 작업, 완료 기준, 예상 난이도를 정리한다.
6. **확인 질문 목록:** 설계 중 판단이 필요한 사항을 모아 질문한다. 임의로 결정하지 않는다.

**운영 중인 서비스 보호 규칙**
- 작업 전 데이터베이스 전체를 백업한다.
- 모든 개발은 개발용 복사본에서 진행하고, 운영 데이터는 건드리지 않는다.
- 운영 반영은 검증이 끝난 뒤, 명시적 승인을 받고 진행한다.

## 1. 배경과 목적

### 1.1 배경
- 운영자는 18년 경력의 AP·Honors·Regular Chemistry 전문 강사다. 학원의 대표 화학 강사이며 화학 담당은 1인이다. 모든 수업 자료와 문항의 저작권은 운영자 본인에게 있다.
- AI 발전으로 개념 설명, 문제 해설, 채점의 가치는 하락하고 있다. 반면 **학생의 약점을 진단하고, 처방하고, 성과를 책임지는 역할**의 가치는 올라가고 있다.
- 운영자의 핵심 병목은 수입과 성과가 본인의 강의 시간에 묶여 있다는 점이다. 이 시스템은 **강사의 진단·관리 역량을 복제해 시간 제약을 푸는 인프라**다.

### 1.2 시스템의 최종 목적
1. **업무 자동화:** 채점, 오답 분석, 리포트 작성 시간을 줄인다.
2. **학생 약점 진단:** 학생이 무엇을 왜 틀리는지를 오류 유형 단위로 진단한다.
3. **성과 관리:** 진단 → 처방 → 재평가로 이어지는 순환 구조로 약점 해소를 확인한다.
4. **학부모 리포트:** 근거 있는 분석 결과를 학부모에게 제공한다.
5. **데이터 자산화:** 학생 응답과 오류 데이터를 누적해, 범용 AI가 가질 수 없는 운영자 고유의 자산으로 만든다.

### 1.3 1단계의 목적
1단계는 최종 형태를 한 번에 만들지 않고, **작동 여부를 검증하면서 데이터를 쌓는 단계**다.
- 문항을 태깅하고, 학생 오답을 오류 코드로 집계해 **데이터를 축적**한다.
- 처방은 **문항은행의 유사 문제 제공**으로 단순화한다.
- 한 학기 운영 후 평가 기준(9장 단계 5)을 통과하면 최종 형태로 확장한다.

### 1.4 성공 기준
- 운영자의 반복 업무 시간이 실제로 줄어드는가
- 학부모가 분석 결과 때문에 등록·재등록하는가
- 처방 후 학생의 약점이 실제로 해소되는가

기능의 완성도는 성공 기준이 아니다. **최소 범위로 빠르게 실제 학생에게 쓰는 것**을 우선한다.

## 4. 핵심 설계 원칙

### 원칙 1. 설계는 최종형, 구현은 최소형
- 데이터 구조는 **최종 형태 전체를 기준으로 설계**한다.
- 실제 테이블과 기능은 **각 개발 단계에서 필요한 것만 만든다.**
- 최종 형태에서 추가되는 기능(약점 상태, 처방, 확인 문항 등)은 대부분 원자료에서 계산되는 **해석 층**이다. 원자료가 빠짐없이 쌓여 있으면 나중에 **과거 데이터로 소급 계산**할 수 있다.
- 최종 형태로 갈 때 해석 층 설계를 일부 수정하는 것은 정상이다. 목표는 "설계를 고치지 않는 것"이 아니라 **"고쳐도 과거 데이터를 잃지 않는 것"**이다.

### 원칙 2. 원자료는 단계 2부터 완전하게 수집한다
- 학생의 원자료(선택한 선택지, 답 변경 이력, 다시 보기 표시, 소요 시간, 확신도, FRQ 답안 이미지·텍스트)는 **절대 덮어쓰지 않고 영구 보존**한다.
- 시험을 보는 순간에만 얻을 수 있는 데이터이므로, **하나라도 빠진 채 출시하면 그 기간의 데이터는 복구할 수 없다.**
- 오류 코드, 집계, 약점 판정 등 해석은 원자료 위에 얹는 별도 층이다.

### 원칙 3. 학생 ID와 FRQ 통합 구조는 설계 단계에서 확정한다
- FRQ 연결 구현은 단계 4로 미루지만, **미루는 것은 구현이지 설계가 아니다.**
- 새 MCQ 기능은 **처음부터 기존 FRQ 시스템과 같은 학생 ID 체계**를 쓴다. 서로 다른 ID 체계로 운영을 시작하면 나중에 합치는 작업이 가장 어렵다.

### 원칙 4. MCQ 학생 기록에는 오류 코드가 아니라 "선택한 선택지 ID"를 저장한다
- 오류 코드는 조회 시점에 문항은행의 선택지 태그에서 가져온다(파생 값).
- 선택지 태그를 수정하거나 새로 입력하면 **과거 모든 응답 기록에 자동 반영**된다.
- 이 덕분에 **모의고사는 태깅이 끝나기 전에 출시할 수 있다.**

### 원칙 5. 모든 기준에 버전을 둔다
- 문항: 수정 시 새 버전으로 등록. 학생 응답은 어느 버전에 대한 것인지 기록한다.
- Error Taxonomy: 코드 체계 버전을 기록한다.
- 스킬 체계: 어느 CED 버전 기준인지 기록한다.

### 원칙 6. 오류 코드는 별도 코드 목록 표로 관리한다
- 코드마다 정의, 판정 기준, 도입 버전, 상태(사용 중 / 폐기)를 저장한다.
- 코드는 삭제하지 않고 폐기 표시만 한다.
- 코드 변경 시 변환표를 둔다.

| 변경 유형 | 예시 | 기존 데이터 처리 |
|---|---|---|
| 정의 수정 | A1 정의 문구 수정 | 자동 반영 |
| 병합 | 두 코드를 하나로 | 자동 변환 |
| 분할 | M3 → M3a, M3b | 자동 변환 불가. "재판정 필요"로 표시 후 원자료로 재판정 |

### 원칙 7. 사람·AI가 판정한 기록은 이력을 쌓는다
- FRQ 오류 판정처럼 판단이 들어간 기록은 수정 시 이전 판정을 지우지 않고 새 판정을 추가한다.
- 판정마다 분류 체계 버전, 판정자(AI / 교사), 판정 시각을 기록한다.

### 원칙 8. 과목에 묶이지 않는 층과 묶이는 층을 분리한다 (Regular/Honors 확장 대비)

| 층 | 과목 공통 여부 | 설계 |
|---|---|---|
| 오류 코드 | 공통 | 화학 전 과정 공용 |
| 개념 태그 | 공통 | 과목 무관 공통 개념 ID (예: `STO-LR` 화학량론-한계 반응물) |
| 과목별 단원 매핑 | 과목별 | 공통 개념 ID → 과목의 단원 (예: `STO-LR` → AP Unit 4 / Honors Unit 6) |
| 스킬 체계 | 과목별 | AP는 Science Practice. Regular/Honors는 비워두거나 추후 자체 체계 |
| 난이도 | 과목별 | 같은 문항도 과목별로 따로 기록 |
| 적용 과목 | 문항별 | 문항 하나에 복수 과목 지정 가능 |

### 원칙 9. 판단은 규칙이, 말은 AI가 한다
- 어떤 문제를 제시할지, 언제 교사에게 넘길지는 **규칙(설정 가능한 표)**이 결정한다.
- AI는 태깅, 풀이 해석, 1차 판정 후보 제시를 담당한다.
- 규칙의 수치는 코드에 하드코딩하지 말고 설정값으로 관리한다.

### 원칙 10. 시험 유형별 차이는 코드가 아니라 설정으로 처리한다
- 확신도 체크, 제한 시간, 참고 자료 제공, 결과 공개 시점, 2단계 추가 문항 등은 **시험 세트 설정값**으로 관리한다.
- 모의고사, 진단고사, 유사 문제 풀이를 별도 프로그램으로 만들지 않는다. **하나의 시험 엔진이 설정에 따라 다르게 동작한다.**

### 원칙 11. 원본 데이터는 데이터베이스에 둔다
- 엑셀은 입력·검수·내보내기 화면으로만 쓴다. 원본 데이터는 데이터베이스에 저장한다.
- 데이터베이스 종류는 기존 FRQ 시스템과의 통합을 고려해 제안할 것.

## 6. Error Taxonomy v0.1

### 6.1 코드 체계: 7개 대분류 + 판정 보류, 총 19개 코드

| 대분류 | 코드 | 세부 유형 | 판정 기준 |
|---|---|---|---|
| **C 개념** | C1 | 오개념 | 틀린 모델을 확신하고 적용 |
| | C2 | 개념 공백 | 해당 개념을 모름, 풀이 시작 불가 |
| | C3 | 개념 혼동 | 비슷한 개념을 바꿔 적용 (예: 분자간 힘과 공유결합) |
| **M 표상·모델** | M1 | 입자 그림 해석 | 분자 모형, 입자 그림을 잘못 읽음 |

| | M3 | 기호·식 변환 | 화학식, 반응식, Lewis 구조로 옮기는 과정의 오류 |

**운영:** 파일럿에서는 대분류 7개로만 태깅한 뒤, 판정 일치도가 확인되면 세부 코드로 내려간다. 코드 체계는 v0.1로 동결하고, 수정은 실제 학생 데이터 검토 후에만 한다.

### 6.2 판정 규칙
1. **예상과 관찰을 분리한다.** 문항은행의 선택지 코드는 "예상 오류"다. 학생이 그 선택지를 고르면 "관찰 오류 후보"가 된다. 1단계에서는 이 후보를 그대로 **집계**에 사용하되, 확정된 약점으로 표현하지 않는다.
2. **학생 확신도는 보조 증거다.**
   - 확신도가 있는 시험(진단고사): 오답 + 확신 있음 → "C1 의심"으로 표시한다.
   - 확신도가 없는 시험(모의고사): 확신도를 추정하거나 임의로 채우지 않는다.
3. **모의고사의 불확실성 대체 신호** (모두 보조 증거이며 단독으로 판정하지 않는다)
   - 다시 보기 표시한 문항
   - 답을 여러 번 바꾼 문항
   - 정답이지만 소요 시간이 해당 문항의 평균보다 크게 긴 문항 → "불안정한 지식" 후보
4. **주 코드 1개, 보조 코드는 독립된 오류만.** 앞선 오류 때문에 생긴 연쇄 오류는 기록하지 않는다. 최초 오류를 주 코드로 한다.
5. **판정이 불확실하면 U1.** 억지로 분류하지 않는다.
6. **서술(E) 코드는 채점 기준에 해당 요구가 있을 때만** 적용한다.
7. **경계 사례 규칙**
   - 문제 문구를 잘못 읽음 → Q1 / 올바로 읽고 계산 중 부호를 틀림 → A2
   - 조건은 읽었지만 그 화학적 의미를 잘못 해석 → Q가 아니라 C 또는 M
   - 개념은 맞고 용어만 틀림 → E3 / 용어 혼동이 실제 개념 혼동 → C3
8. **"Careless mistake" 같은 모호한 코드는 쓰지 않는다.**
9. **시간 압박, 시험 불안 같은 학생 단위 현상은 문항 태그로 붙이지 않는다.** 5.8절 지표로 계산한다.

### 6.3 확정 경로 (최종 형태 기준, 1단계에서는 참고)
- **진단고사 (MCQ, 확신도 있음):** 선택지 예상 코드 + 학생 확신도 + 2단계 추가 문항 결과로 판단한다.
- **모의고사 (MCQ, 확신도 없음):** 선택지 예상 코드 + 대체 신호 + 반복 기록으로 판단한다. 시험 중 추가 질문이 불가능하므로 **확인 질문 대신 확인 문항**을 배정한다.
- **FRQ:** AI가 채점 포인트별 오류 코드 후보를 제안 → 교사가 확정.
- **챗봇·AI 튜터:** 후보 코드 설정 → 짧은 진단 질문 → 확정.

### 6.4 약점 상태 단계 (최종 형태에서 구현, 1단계에서는 설계만)

| 상태 | 조건 (초기 설정값) | 다음 행동 |
|---|---|---|
| 관찰됨 | 한 번의 답안에서 확인 | 기록만 |
| 반복 의심 | 서로 다른 문항 2개 이상, 가능하면 다른 시험·세션에서 같은 코드 | 확인 문항 배정 |
| 확인된 패턴 | 확인 문항 또는 재학습 후 새 문항에서도 재발 | 처방 시작, 학부모 리포트 게재 |
| 개선 확인 | 처방 후 1주 이상 간격, 새 문항 2개 연속 정답 | 해소 기록, 이후 불시 재확인 |

리포트에는 "확인된 패턴"만, 반드시 근거와 함께 게재한다.
예: "최근 서로 다른 시험 3문항 중 2문항에서 몰 비 설정 오류(P1)가 확인되었고, 확인 문항에서도 재발함."

### 6.5 처방표 (최종 형태에서 구현, 1단계에서는 설계만)

| 코드 | 기본 처방 | 담당 |
|---|---|---|
| C1 | 반례 제시, 결과 예측 후 확인 과제 (반복 풀이로는 고쳐지지 않음) | 교사 우선 |
| C2 | 개념 재학습, 기본 문제 | AI |
| C3 | 비교·대조표, 구분 문제 | AI |
| M1~M3 | 표상 간 변환 연습 | AI + 교사 점검 |
| P1 | 계산 없이 풀이 설정만 쓰는 연습 | 교사 우선 |
| P2 | 풀이 순서·결과 타당성 점검 루틴 | AI |
| Q1~Q2 | 조건 표시 루틴, 질문 재진술 | AI |
| A1~A3 | 단위 추적 루틴, 검산 습관 | AI |
| E1~E3 | AP 채점 기준 기반 첨삭, 모범 답안 비교 | 교사 (AI 1차 첨삭) |
| X1~X2 | 실험 설계 사례 분석 | 교사 검토 |
| U1 | 확인 문항 배정 또는 교사 확인 | 교사 |

**교사 개입 요청 조건:** AI 처방 후에도 해결되지 않음 / U1로 판정이 남음 / 여러 코드가 얽힘.

### 6.6 1단계 처방: 유사 문제 제공 규칙 (단계 3에서 구현)

**① 유사 문제는 문항은행에서만 선택한다.** AI가 새로 생성한 문제는 1단계에서 사용하지 않는다.

**② 선택 규칙 (위에서부터 순서대로 적용)**
1. 같은 개념 + 같은 오류 코드
2. 같은 개념 + 다른 오류 코드
3. 같은 오류 코드 + 인접 개념
4. 해당 문항 없음 → "보충 필요" 기록, 교사가 보충

- 학생이 이미 푼 문항은 제외한다.
- 배정 개수, 인접 개념의 정의는 설정값으로 관리한다.

**③ 유사 문제는 반드시 시스템 안에서 풀게 한다.** PDF 배포는 하지 않는다. 풀이 결과가 그대로 재평가 데이터(5.6절)가 된다.

**④ 모든 오류 코드에 유사 문제를 배정한다. C1·E 계열은 다음을 적용한다.**
- **C1 오개념:** 유사 문제를 배정하고, 교사 화면에 **"교사 확인 필요"** 표시를 **병행**한다. 같은 유형의 반복이 오개념을 굳힐 위험이 있으므로 운영자가 확인할 수 있게 하기 위함이며, 처방을 막지 않는다. 운영자 판단에 따라 표시 기능은 끌 수 있도록 설정값으로 둔다.
- **E 서술 오류:** FRQ 문항은행에서 유사 FRQ를 배정하고, **기존 FRQ 자동 채점기로 채점**한다. FRQ 채점기가 통합되는 **단계 4부터** 제공한다.
- 1단계 평가(단계 5)에서 C1·E 계열의 재발률을 다른 코드와 비교해, 유사 문제 처방이 이 계열에도 효과가 있는지 확인한다.

**⑤ "보충 필요" 조합 목록을 출력한다.** 유사 문제가 없어 규칙 4에 도달한 조합은, 운영자가 새로 만들어야 할 문항 목록이 된다.

| 기능 | 구현 단계 |

### F1. PDF 문항 추출 파이프라인
- 문제지 PDF와 답지 PDF를 문항 단위로 분리하고, 정답과 짝을 맞춘다.
- 그림·그래프는 이미지로 잘라 문항에 연결한다.
- 화학식의 아래첨자·위첨자·전하·반응 화살표를 정확히 보존한다.
- 파일마다 형식이 다를 수 있으므로 파일 유형별 추출 규칙을 허용한다.
- 추출 결과는 사람이 검수할 수 있는 형태로 출력한다.
- **추출 결과는 시험 엔진과 태깅 파이프라인이 공유한다. 추출은 한 번만 한다.**
- 단계 2에서는 모의고사 2~3세트만 추출해 규칙을 안정시킨 뒤, 단계 3에서 나머지를 일괄 처리한다.

### F2. 문항은행·시험 세트 관리
- 문항 등록, 수정(새 버전 생성), 상태 변경, 검수
- 엑셀 내보내기·가져오기(검수용)
- 문항 필터: 과목, 단원, 개념, 스킬, 유형, 상태, 검토 필요 여부
- 시험 세트 구성과 설정 관리 (5.2절)

### F3. 태깅 파이프라인
- 문항마다 AI API를 호출해 태깅한다. 모든 호출에 **같은 태깅 기준서(`tagging_guide.md`)와 검수된 예시 문항**을 넣는다.
- 결과는 정해진 JSON 형식으로만 받는다.
- 자동 검증:
  - 코드 목록에 없는 코드 사용 시 거부
  - 계산 문항은 정답을 코드로 재계산해 검증
  - 태깅 확신도가 낮으면 "검토 필요" 표시
- MCQ 오답 선택지 분석: 선택지마다 오류 경로를 역산해 "명확 / 약함 / 진단력 없음"으로 분류
- 진단력 없는 선택지에 대해 **교체안**을 생성할 수 있다.
  - 정답과 겹치거나 해석에 따라 정답이 될 수 있는 선택지는 금지
  - 정답과 지나치게 가까운 값(유효숫자 차이 수준) 금지
  - 가능하면 한 문항의 오답들이 서로 다른 오류 코드를 가리키도록
  - **원본은 보존하고 교체본은 새 버전으로 등록.** 교체 반영은 교사 승인 후
- 문항별 결과를 즉시 저장해 중단 후 재개 가능하게 한다.
- 기준 수정 시 해당 범위만 재실행할 수 있게 한다.
- 대량 실행 전 50문항 시범 실행으로 품질과 비용을 보고한다.
- 대량 처리에는 Sonnet 급 모델, 비용 절감이 필요하면 Batch API 사용을 검토한다. 사용량·비용 상한을 설정한다.

### F4. 시험 엔진과 UI

**공통 필수 기능 (단계 2)**
- 학생 식별 (기존 FRQ 시스템과 같은 학생 ID), 시험 세트 선택
- 문항 표시: 그림·그래프, 화학식 첨자·전하의 정확한 렌더링
- 선택지 선택, 문항 이동, 문항 목록(응답·미응답·다시 보기 표시 현황)
- **다시 보기 표시 기능** (모의고사의 핵심 불확실성 신호이므로 눈에 잘 띄고 쉽게 누를 수 있게)
- **자동 저장과 이어서 응시:** 네트워크 끊김, 기기 재시작 후에도 끊긴 지점부터 재개
- **타이머와 문항별 소요 시간 기록**
- **선택한 선택지 ID와 답 변경 이력 저장**
- AP 실전과 같은 참고 자료(주기율표, 공식표) 열람
- 제출 후 규칙 기반 자동 채점 (MCQ 채점에 AI를 쓰지 않는다)
- 학생 결과 화면 (단계 2에서는 점수 중심)
- 태블릿·PC 모두 사용 가능한 반응형 UI

**설정에 따라 동작하는 기능 (단계 3)**
- **학생 확신도 체크:** 설정이 켜진 시험(진단고사)에서만 표시한다. 문항당 한 번의 탭으로 끝나도록 설계해 응시 흐름을 방해하지 않게 한다.
- 2단계 추가 문항: 진단고사에서 판정 경계 학생에게만 제시
- 유사 문제 풀이 모드 (F6)

**태깅이 완료되지 않은 문항도 시험에 사용할 수 있어야 한다.** (원칙 4)

### F5. 단순 집계 화면 (교사용, 단계 2)
- 학생별: 오류 코드별 발생 횟수, 개념별 정답률
- 반별: 가장 많이 발생한 오류 코드, 가장 약한 개념
- 오류 코드는 "관찰 오류 후보"의 집계이며, 확정된 약점으로 표현하지 않는다.
- 태깅이 새로 입력되면 과거 응시 기록까지 자동으로 다시 집계된다.

### F6. 유사 문제 제공 (단계 3)
- 6.6절 규칙에 따라 오답 문항별로 유사 문제를 배정한다. **모든 오류 코드가 대상이다.**
- 학생은 시스템 안에서 유사 문제를 풀고, 결과는 5.6절 형식으로 저장한다.
- C1 계열은 유사 문제 배정과 함께 "교사 확인 필요" 표시를 병행한다(설정으로 끌 수 있음).
- E 계열(FRQ)의 유사 문제는 단계 4에서 FRQ 채점기와 연결해 제공한다.
- "보충 필요" 조합 목록을 교사 화면에서 확인할 수 있게 한다.

### F7. FRQ 채점기 연결 (단계 4)
- 기존 FRQ 데이터를 통합 구조로 이전한다 (백업 후, 개발 환경에서 검증).
- FRQ 문항을 파트·채점 포인트 단위로 태깅한다.
- 채점 결과에 채점 포인트별 오류 코드 후보를 함께 출력한다.
- 판정자는 AI로 기록하고, 교사가 확정·수정할 수 있게 한다.
- 파트 의존성을 이용해 연쇄 오류를 구분한다.
- 과거 FRQ 답안 원본이 보존되어 있다면, 과거 답안에도 소급해 오류 코드를 붙인다.
- MCQ·FRQ 통합 집계를 제공한다.

## 8. 비기능 요구사항

- **응시 안정성:** 모든 시험이 디지털로만 진행되므로, 응답은 선택 즉시 저장하고 네트워크가 끊겨도 응답이 유실되지 않아야 한다. 재접속 시 남은 시간과 응답 상태를 정확히 복원한다.
- **기기 호환:** 학원 보유 태블릿·PC와 학생 개인 기기에서 동일하게 동작해야 한다. 지원 브라우저·기기 범위를 확인 질문으로 올릴 것.
- **개인정보:** 학생 실명 대신 식별자 사용. 권한별 열람 범위 분리(학생 / 학부모 / 교사 / 보조 강사). 만 14세 미만 학생의 개인정보는 보호자 동의가 필요하므로, 동의 여부를 기록할 수 있어야 한다.
- **백업:** 정기 자동 백업. 스키마 변경 전 수동 백업.
- **환경 분리:** 개발 환경과 운영 환경 분리.
- **스키마 변경 관리:** 데이터베이스 구조 변경은 마이그레이션 도구로 버전을 관리한다. 단계마다 테이블이 추가되므로 필수다.
- **비용 관리:** AI API 사용량과 비용 기록, 상한 설정.
- **로그:** 태깅·판정·문항 수정 이력 기록.
- **저작권:** 출처 필드(선택 입력)에 기출·교재로 표시된 문항은 학생 배포 여부를 별도로 관리할 수 있게 한다.

## 9. 단계별 개발 계획

### 전체 흐름

| 단계 | 이름 | 핵심 |
|---|---|---|
| 0 | 현황 분석 | 기존 FRQ 시스템 파악 |
| 1 | 통합 데이터 구조 설계 | **최종 형태 기준으로 설계** |
| 2 | 모의고사 MVP | 모의고사 2~3세트로 첫 출시 |
| 3 | 문항은행 확장 | 전체 문항 태깅, 유사 문제, 진단고사 |
| 4 | FRQ 연결 | 기존 FRQ 채점기 통합 |
| 5 | 1단계 평가 | 한 학기 운영 후 최종 형태로 갈지 판단 |
| 6~ | 최종 형태 | 평가 통과 후 |

### 단계 0. 현황 분석

| 작업 | 완료 기준 |
|---|---|
| 기존 FRQ 채점 시스템의 구조, 데이터, 학생 계정 방식, 답안 원본 보존 여부 분석 | 현황 분석서 승인 |

### 단계 1. 통합 데이터 구조 설계

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 1-1 | 최종 형태 기준 데이터 구조 설계 (5장 전체), 테이블별 구현 시점 표시 | 설계 문서 승인 |
| 1-2 | 기존 FRQ 데이터 이전 계획 (실행은 단계 4) | 이전 계획 승인 |
| 1-3 | **학생 계정·ID 통합 방식 결정** | 새 MCQ 기능이 기존 FRQ와 같은 학생 ID를 쓰도록 확정 |

이 단계의 산출물은 문서다. 실제 데이터베이스는 각 단계에서 필요한 부분만 만든다.

### 단계 2. 모의고사 MVP (첫 출시)

**목표:** 모의고사 2~3세트로 실제 학생이 시험을 보고, 원자료가 쌓이기 시작하는 것.

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 2-1 | 데이터베이스 기반 구축: 기준 데이터, 문항은행(MCQ), 선택지, 시험 세트, 학생 응답 원자료, 오류 코드 목록, 판정 기록 구조 | 개발 환경에 생성 완료 |
| 2-2 | PDF 추출 v1: 모의고사 2~3세트만 추출 | 운영자 검수 완료. 화학식·그림이 정확함 |
| 2-3 | 시험 엔진과 UI: **모의고사 설정만 구현** (확신도 없음) | 문항 표시, 다시 보기 표시, 타이머, 자동 저장, 끊긴 지점부터 재개 작동 |
| 2-4 | **원자료 저장 검증:** 선택지 ID, 문항 버전, 소요 시간, 답 변경 이력, 다시 보기 표시 | 테스트 응시 기록이 빠짐없이 저장됨 |
| 2-5 | 규칙 기반 자동 채점, 학생 결과 화면(점수 중심) | 채점 오류 없음 |
| 2-6 | **소수 학생 실사용 테스트** (5~10명) | 응답 유실 없음, 불편 사항 수정 |
| → | **첫 출시** | 태깅 없이도 출시 가능 |

**동시 진행 (채팅에서 운영자와 AI가 진행)**

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 2-7 | 태깅 파일럿: 추출한 2~3세트 중 20~30문항을 태깅하고 검수 | 운영자와 AI의 판정 일치도 확인 |
| 2-8 | 태깅 기준서(`tagging_guide.md`) 확정 → 프로젝트에 추가 | 기준서 완성 |

**출시 후**

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 2-9 | 태깅 파이프라인 v1: 2~3세트 전체 태깅 → 데이터베이스 입력 | 샘플 검수 통과 |
| 2-10 | 단순 집계 화면 (F5) | 운영자가 수업 계획에 쓸 수 있는 수준. 과거 응시 기록까지 자동 집계됨 |

**유사 문제 제공은 단계 2에 넣지 않는다.** 2~3세트 분량으로는 "같은 개념 + 같은 오류 코드" 조합의 문항이 거의 없어 기능이 제대로 작동하지 않는다.

### 단계 3. 문항은행 확장

**목표:** 전체 문항을 태깅하고, 유사 문제와 진단고사를 가동하는 것.

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 3-1 | 나머지 PDF 일괄 추출 (단계 2에서 안정된 추출 규칙 사용) | 검수 완료 |
| 3-2 | 전체 일괄 태깅: 50문항 시범 → 전체 실행 → 5~10% 샘플 검수 | 검수 통과, 비용 확인 |
| 3-3 | **유사 문제 제공 (F6):** 6.6절 규칙, 시스템 안에서 풀이 | 학생이 오답 후 유사 문제를 풀고 결과가 저장됨 |
| 3-4 | C1 계열 오류에 "교사 확인 필요" 표시 병행 (유사 문제 배정과 함께) | 교사 화면에 표시됨, 설정으로 켜고 끌 수 있음 |
| 3-5 | "보충 필요" 조합 목록 출력 | 보충할 문항 목록 확보 |
| 3-6 | **진단고사 설정 추가:** 확신도 체크, 2단계 추가 문항 | 같은 시험 엔진으로 진단고사 응시 가능 |

### 단계 4. FRQ 연결

**목표:** 운영 중인 FRQ 채점기를 통합 구조에 연결하는 것.

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 4-1 | 기존 FRQ 데이터를 통합 구조로 이전 (백업 후, 개발 환경에서 검증) | 데이터 손실 없음, 운영 중단 없음 |
| 4-2 | FRQ 문항을 파트·채점 포인트 단위로 태깅 | 검수 완료 |
| 4-3 | 채점기가 채점 포인트별 오류 코드 후보를 출력, 운영자가 확정 | 교사 확정 화면 작동 |
| 4-4 | 과거 FRQ 답안 소급 태깅 (답안 원본이 보존된 경우) | 소급 완료 |
| 4-5 | **FRQ 유사 문제 제공:** E 계열 등 FRQ 오답에 유사 FRQ를 배정하고 FRQ 채점기로 채점 | 풀이 결과가 5.6절 형식으로 저장됨 |
| 4-6 | MCQ·FRQ 통합 집계 | 학생별 통합 오류 현황 확인 |

### 단계 5. 1단계 평가 (한 학기 운영 후)

다음 기준으로 최종 형태로 넘어갈지 판단한다.

| 점검 항목 | 확인하는 것 |
|---|---|
| 태깅 품질 | 운영자와 AI의 태깅 일치도 |
| 학생 사용률 | 배정된 유사 문제를 실제로 푼 비율 |
| 처방 효과 | 유사 문제 풀이 후 같은 오류 코드의 재발률이 줄었는가 |
| C1·E 계열 효과 | C1·E 계열의 재발률 감소가 다른 코드와 비슷한가. 현저히 낮으면 최종 형태에서 이 계열의 처방을 교사 개입 중심으로 바꾼다 |
| 업무 시간 | 채점·분석에 쓰던 시간이 실제로 줄었는가 |
| 데이터 공백 | 유사 문제가 없어 보충이 필요했던 조합의 수 |

- 학생 사용률이 낮으면 기능보다 운영 방식(과제 연동 등)을 먼저 고친다.
- 처방 효과가 없으면 최종 형태로 가기 전에 오류 분류 자체를 재검토한다.

**이 평가에 필요한 지표를 계산할 수 있도록, 단계 2~4의 데이터 구조가 이를 지원해야 한다.**

### 단계 6~. 최종 형태 (평가 통과 후)

다음 순서로 구현한다. 모두 원자료에서 계산되는 해석 층이므로 **과거 데이터에 소급 적용**한다.
1. 약점 상태 판정 (6.4절)
2. 처방표와 확인 문항 배정, 교사 개입 추천 (6.5절)
3. 교사용 약점 대시보드, 학부모 리포트 자동 생성
4. 2단계 객관식 문항 (답 + 이유 선택)
5. AI 튜터, 학생 질의응답 챗봇
6. 학교 내신 성적 연결, 벤치마크
7. Regular/Honors Chemistry 확장

## 10. 미결정 사항 (설계 중 확인 질문으로 올릴 것)

1. 선택지를 교체할 때는 원본 문항을 보존하고, 진단용 변형본을 새 버전 또는 별도 문항으로 등록하는 방식 중 무엇을 쓸지
2. 학생 로그인 방식과 계정 관리 (기존 FRQ 시스템 방식 기준)
3. 배포 환경과 기존 FRQ 서비스의 호스팅 방식
4. 모의고사에서 FRQ를 응시하는 방식 (기존 FRQ 채점기의 답안 입력 방식과 맞출 것)
5. 진단고사 확신도 척도 (기존 진단고사 설계와 동일하게)
6. 지원 기기·브라우저 범위
7. 데이터베이스와 마이그레이션 도구 선택 (기존 시스템 분석 후 제안)
8. 단계 2에서 사용할 모의고사 2~3세트의 선정
9. 유사 문제 배정 개수와 "인접 개념"의 정의
10. `tagging_guide.md`는 단계 2의 태깅 파일럿 후 채팅에서 작성해 제공 예정

## 11. 용어

| 용어 | 의미 |
|---|---|
| MCQ / FRQ | 객관식 / 서술형 문항 |
| 모의고사 | AP 실전 대비 시험. 실전 조건 재현을 위해 확신도 체크 사용 안 함 |
| 진단고사 | AP Chemistry 수강 가능 여부를 판정하는 시험. 확신도 체크 사용 |
| 시험 세트 | 문항 구성과 설정(시간, 확신도 사용 여부 등)을 묶은 단위 |
| 1단계 | 태깅 → 단순 집계 → 유사 문제 제공까지의 범위 (개발 단계 2~4) |
| 최종 형태 | 약점 상태 판정, 처방표, AI 튜터 등을 포함한 전체 시스템 (개발 단계 6~) |
| 해석 층 | 원자료에서 계산되는 값 (오류 집계, 약점 상태, 처방 등). 소급 계산 가능 |
| CED | College Board의 AP Course and Exam Description (공식 교육과정 문서) |
| Science Practice | CED에 정의된 AP Chemistry의 6개 과학 탐구 역량 |
| Error Taxonomy | 오류 유형 분류 체계 (6장) |
| 예상 오류 | 문항은행에서 선택지·채점 포인트에 미리 붙인 오류 코드 |
| 관찰 오류 후보 | 학생이 고른 선택지에서 파생된 오류 코드. 확정된 약점이 아님 |
| 학생 확신도 | 학생이 자기 답을 얼마나 확신하는지 (자기 보고, 진단고사에서만 수집) |
| 진단 확신도 | 오류 판정이 얼마나 확실한지 |
| 불확실성 대체 신호 | 확신도가 없는 시험에서 참고하는 다시 보기 표시, 답 변경 이력, 소요 시간 |
| 연쇄 오류 | 앞선 오류 때문에 뒤따라 발생한 오류 (별도 기록하지 않음) |
| 유사 문제 | 오답 후 문항은행에서 규칙에 따라 배정하는 문항. 시스템 안에서 풀이 |
| 보충 필요 조합 | 유사 문제가 없어 새 문항 제작이 필요한 개념 × 오류 코드 조합 |
| 2단계 문항 | 답을 고른 뒤 그 이유를 선택지로 다시 고르는 진단 문항 (최종 형태) |
| 확인 문항 | 약점을 확정하기 전에 그 약점이 진짜인지 확인하기 위해 배정하는 문항. 특정 오류를 가진 학생만 특정 오답을 고르도록 설계된 문항을 쓴다 (최종 형태). 1단계에서는 유사 문제의 풀이 결과가 확인 데이터 역할을 겸한다 |
